# План: вход через гостя, Discord и Telegram

Статус: реализовано локально 2026-11-11 (задачи 28–31), ветка alias/auth. Живой вход ждёт задачи 27 (сервер, домен, ключи). Уведомление РКН подаёт пользователь.

## Цель

Три способа войти: **Гость** (только имя), **Discord** и **Telegram** (ник и аватар). Мы не собираем телефоны, почту и другие данные. Взлом сервера не должен давать ценную базу пользователей.

## Как это работает для игрока

1. На главной странице кнопки: «Играть как гость», «Войти через Discord», «Войти через Telegram».
2. **Гость** вводит имя, как сейчас. Ничего не сохраняется, кроме cookie комнаты.
3. **Discord / Telegram**: подтверждение на стороне сервиса, возврат на сайт. Имя и аватар подставляются сами, имя можно поправить перед игрой.
4. В комнате игрок с аккаунтом показан с аватаркой. Остальные люди за тем же компьютером добавляются как гости, по-прежнему.
5. «Выйти из аккаунта» в шапке: сессия удаляется на сервере сразу.

Модель «игрок ≠ устройство» сохраняется: аккаунт привязан к **игроку**, а не к устройству. Один браузер — не больше одного аккаунта; гостей рядом можно сколько угодно.

## Что получаем от сервисов

| Сервис | Механизм | Что берём | Чего нет и не будет |
| --- | --- | --- | --- |
| Discord | OAuth2 Authorization Code + PKCE + `state`, scope **только `identify`** | id, `global_name`/`username`, хэш аватара | email (scope `email` не запрашиваем), гильдии, сообщения |
| Telegram | Telegram Login Widget, проверка подписи HMAC-SHA256 ключом от токена бота, `auth_date` не старше 5 мин | id, `first_name`, `username`, `photo_url` | **телефон**: Telegram не передаёт его сайтам; пользователь вводит номер только на сайте Telegram |

Токен доступа Discord используется один раз для запроса профиля и **сразу выбрасывается**, нигде не сохраняется.

## Решения пользователя (2026-11-11)

- Аккаунты хранятся постоянно, вход запоминается (сессия 30 дней, продлевается при использовании).
- База: пользователь предлагает **PostgreSQL** с усиленным слоем безопасности. Ждёт подтверждения: нужна npm-зависимость `pg` (см. ниже).
- Аватары проксируются через наш сервер.
- Код пишем сейчас, живой вход проверяем после переезда на домен.
- В комнате показываются имя и @username.

## Хранение: PostgreSQL

Постоянная база помнит аккаунт между входами: статистику, историю партий, будущие платные функции и блокировки. «Не входить каждый раз» обеспечивает сессия на 30 дней; выбор СУБД на это не влияет.

**Цена PostgreSQL для проекта:**

- Нужна зависимость `pg` (node-postgres). Это меняет правило AGENTS.md «внешние зависимости для запуска не нужны»: появятся `npm ci` и `package-lock.json`.
- Отдельная служба на VPS, миграции, резервные копии `pg_dump`.
- Тесты: интеграционные — на локальном PostgreSQL (Docker или Homebrew); юнит-тесты — на хранилище в памяти за тем же интерфейсом.

Альтернатива без зависимостей — SQLite (`node:sqlite`, Node 24): для одного VPS по безопасности и удобству то же самое. Переход на PostgreSQL позже займёт одну задачу, если хранилище спрятать за интерфейсом `AccountStore`.

**Слой безопасности PostgreSQL** (в дополнение к общему списку ниже):

- Слушает только `127.0.0.1`/unix-сокет, порт наружу закрыт файрволом; вход `scram-sha-256`.
- Две роли: `alias_migrator` (DDL, только при деплое) и `alias_app` (только `SELECT/INSERT/UPDATE/DELETE` на своих таблицах, без `CREATE`, без доступа к другим БД).
- Только параметризованные запросы, без сборки SQL строками.
- Шифрованные резервные копии (`pg_dump` + `age`/`gpg`), хранение 14 дней.

Таблица `accounts` — всё, что храним:

- `id` — наш случайный UUID;
- `provider` — `discord` | `telegram`;
- `provider_key` — **HMAC-SHA256(секрет сервера, id у провайдера)**, а не сам id. Утёкший файл без секрета нельзя сопоставить с реальными аккаунтами;
- `display_name`, `username` (@ник), `avatar` (байты картинки до 64 КБ, скачанные при входе и отдаваемые нашим сервером);
- `created_at`, `last_login_at`.

Таблица `sessions`: SHA-256 от токена сессии (сам токен только в cookie), `account_id`, срок действия.

Комнаты и партии остаются в памяти, как сейчас.

## Слой безопасности

- **Нечего красть**: нет паролей, телефонов, почты, токенов провайдеров. Id провайдера хранится только как HMAC.
- **Секреты** (`DISCORD_CLIENT_SECRET`, `TELEGRAM_BOT_TOKEN`, `AUTH_SECRET`) — только в переменных окружения на сервере (`/etc/alias/env`, права 600), не в git.
- **Сессии**: случайный токен 32 байта, cookie `HttpOnly; Secure; SameSite=Lax` (Lax нужен для возврата из Discord), срок 30 дней, отзыв при выходе, ротация при входе.
- **OAuth**: `state` и PKCE против подмены, точный redirect URI, проверка подписи и свежести данных Telegram.
- **База**: файл вне веб-каталога, права 600, пользователь службы без shell; только параметризованные запросы; ежедневная резервная копия.
- **Защита от перебора**: ограничение частоты запросов на `/auth/*` в Node и в Nginx.
- **CSP**: разрешить только `telegram.org`/`oauth.telegram.org` для виджета входа. Аватары сервер скачивает сам (только с `cdn.discordapp.com` и `t.me`, лимит размера и типа) и отдаёт с `/avatars/<id>`. Браузеры друзей к Discord/Telegram не обращаются.
- **Удаление аккаунта** кнопкой: запись стирается полностью.
- Тесты: подделанная подпись Telegram, устаревший `auth_date`, чужой `state`, повтор кода, утечка id провайдера в ответах API, удаление аккаунта.

## Зависимости и порядок

Discord и Telegram требуют **HTTPS-домен**: redirect URI Discord и `/setdomain` у бота Telegram. Поэтому:

1. **27 — сервер и домен** (уже запланированная отдельная задача): новый VPS, домен, HTTPS.
2. **28 — аккаунты и сессии**: `AccountStore` (в памяти + PostgreSQL), миграции, сессии, гость, выход, удаление, ADR о хранении.
3. **29 — Discord**: можно разрабатывать локально (Discord разрешает `http://localhost` как redirect).
4. **30 — Telegram**: локально проверяется только подпись; живой вход — на домене.
5. **31 — интерфейс и документы**: экран входа, аватарки в комнате, обновление политики конфиденциальности и cookies, глоссарий.

Пункты 28–29 можно делать до готовности домена.

## Что нужно от владельца

- Discord: приложение в Developer Portal → `Client ID`, `Client Secret`, redirect URI.
- Telegram: бот через @BotFather → токен, `/setdomain` на будущий домен.
- Домен и новый сервер (задача 27).

## Правовое

Id в Discord/Telegram, ник и аватар — персональные данные по 152-ФЗ. Для граждан РФ закон требует хранить такую базу на сервере в России (локализация). Также нужно уведомить Роскомнадзор об обработке данных. Это влияет на выбор страны нового VPS. Это не юридическая консультация, перед запуском трафика стоит уточнить у юриста.
